모델 구조를 바꿔 가며 추론 성능을 측정하려 했다. 그런데 같은 모델을 같은 옵션으로 다시 실행해도, 가끔 시간이 길어졌다. 대부분은 비슷한데 몇 번만 느렸다. 이 차이가 구조의 효과보다 크다면, 그 위에서 찾아낸 성능 법칙은 시스템의 일시적인 상태를 설명하는 규칙일 수도 있다.

그렇게 아키텍처 탐색을 준비하던 작업이 로그, CPU 이동, 예열, 주파수를 비교하는 실험으로 이어졌다. 이 글은 그 과정에서 확인한 사실과 남겨 둔 질문, 그리고 진단을 끝낸 기준을 정리한 기록이다.

결과부터 말하면 **CPU의 실행 상태는 GPU 추론 벤치마크에도 영향을 줬다. 다만 모든 지연을 하나의 원인으로 설명하지는 못했다.** 기존 자료가 목표로 한 10% 수준의 구조 차이를 탐색할 근거를 제공한다고 판단해 측정 규약을 고정하고 진단을 종결했다.

## 출발점: 에이전트가 성능 법칙을 찾게 하려면

<Q>모델 최적화 실험을 하려다 왜 측정 환경부터 조사했나?</Q>

장기 목표는 Jetson Orin Nano와 Snapdragon Elite NPU 노트북에 적합한 모델 구조와 실행 조건을 찾는 것이다. 우선 RTX PRO 6000 Blackwell에서 후보 생성과 측정 파이프라인을 검증했다. RTX에서 빠른 구조가 두 타깃에서도 빠르다는 가정은 하지 않았다.

후보 공간은 dense Llama 계열의 decoder-only Transformer로 제한했다. 헤드 차원, 헤드 수, GQA 비율, MLP 비율, 레이어 수, 양자화, 시퀀스 길이를 바꾼다. 여기서 GQA 비율은 Q 헤드 수를 KV 헤드 수로 나눈 값이다.

초기 명세는 **25개 구조, 75개 고유 GGUF, 100개 실행 조건**이다. 구조마다 길이 512에서 F16·Q8_0·Q4_0을 비교하는 75개 조건에, 다른 길이를 보는 25개 조건을 더했다. 실제 첫 RTX 파일럿에는 작은·중간·큰 구조의 9개 GGUF와 12개 실행 조건을 사용했다. prefill과 decode를 나누므로 분석 항목은 24개다. 100개 후보 전체를 이미 측정했다는 뜻은 아니다.

GGUF는 실행 파일이 아니라 모델 데이터다. llama.cpp 실행기를 백엔드에 맞게 빌드한 뒤, 각 구조의 무작위 가중치를 GGUF로 생성해 로드했다. 무작위 가중치는 계산 비용을 탐색하기 위한 것이며, 문장 품질을 평가하지 않는다. 학습된 가중치와 같은 실행 경로와 성능을 보이는지도 아직 별도 검증이 필요하다.

그 위에서 검증하려던 연구 질문은 두 가지였다.

- **H1:** 에이전트가 기호 회귀(PySR)보다 적은 측정으로 roofline 예측의 잔차를 설명하는 규칙을 찾는가? 여기서 잔차는 계산량·메모리 이동량으로 예상한 비용과 실제 측정의 차이다.
- **H3:** 에이전트는 노이즈를 법칙으로 오인하거나, 자신이 만든 가설을 반박할 실험을 회피하는가?

측정이 흔들리면 두 질문 모두 해석하기 어려워진다. 먼저 측정값이 무엇을 의미하는지 정해야 했다.

## 같은 모델을 반복한다는 것

<Q>반복 횟수는 무엇을 기준으로 세었나?</Q>

실험 환경은 RTX PRO 6000 Blackwell 96GB, Intel Core i9-10900X, CUDA 13, NVIDIA 드라이버 580.173.02였다. llama.cpp는 커밋 `48e985756788b4a6c50933a88e0af1aa8412b68d`로 고정했다. 전체 레이어 GPU offload, CPU 스레드 4개, batch 512, ubatch 128, flash attention off, KV cache F16을 사용했다. 시스템 클록·governor 정책은 바꾸지 않았다.

prefill은 입력 S개 토큰을 처리하는 시간이다. decode는 길이 S의 KV 상태를 준비한 뒤 64 step을 진행하는 시간으로, 컨텍스트 길이는 S부터 S+63까지 늘어난다. 아래 decode 수치는 별도 표기가 없으면 **토큰 하나가 아니라 64 step 전체 시간**이다.

초기 반복 지연을 보고 후속 프로토콜에서는 새 프로세스마다 25회 실행해 앞 20회를 고정 예열로 분류하고, 뒤 5회를 보존했다. 원본 25회도 모두 남겼다. 느린 표본을 보고 선택적으로 버린 것은 아니다.

분석 단위도 구분했다.

```text
독립 프로세스 1개
  ├─ 앞 20회: 고정 예열, 원자료 보존
  └─ 뒤  5회: 평균 → 프로세스 대표값 1개

독립 프로세스 10개
  └─ 대표값 10개의 중앙값 → 해당 조건의 대표 시간
```

프로세스 하나의 5개 반복은 실행 상태를 공유한다. 따라서 10개 프로세스에서 얻은 50개 타이밍을 독립 실험 50회로 세지 않았다. 새 프로세스라도 같은 세션의 시간 변화까지 독립인 것은 아니므로, 이 구분만으로 모든 상관 문제가 사라지는 것도 아니다.

## 3회에서는 안정적이었는데 10회에서는 왜 달라졌나

<Q>더 많이 측정했더니 안정성 통과율이 떨어졌다. 환경이 나빠진 것일까?</Q>

이전 3라운드와 동일한 조건을 새로운 10라운드로 반복했다. 24개 항목에 각각 새 프로세스 10개, 총 240개 프로세스다. 원본 타이밍은 6,000개, 예열 뒤 보존한 타이밍은 1,200개였다.

| 지표 | 관측 결과 |
| --- | --- |
| 이전 대비 대표값 변화의 절댓값 중앙값 | 약 0.12% |
| 이전 대비 대표값 변화의 최대 절댓값 | 약 1.24% |
| 기존 안정성 표시를 통과한 항목 | 22/24 → 17/24 |

기존 안정성 표시는 라운드 간 상대 범위와 프로세스 내부 변동계수(CV)가 각각 5% 이하인지 보는 기술적 기준이었다. 통계적 동등성 검정은 아니었다.

최댓값이나 범위에 의존하는 기준은 관측 횟수가 늘수록 드문 지연을 만날 기회도 늘어난다. 실제로 새 10라운드에서 3라운드를 고르는 모든 120개 조합을 보면, 통과 항목 수는 20~24개였다. 이전의 22개도 그 안에 있었다. 조합끼리 표본을 공유하므로 이를 독립적인 120회 재현 실험으로 해석하지는 않았다.

여기서 첫 교훈을 얻었다. **대표 성능이 재현되는 것과 드문 지연이 없는 것은 서로 다른 주장이다.** 반복을 늘린 뒤 통과 수가 줄었다는 사실만으로 환경이 악화됐다고 말할 수 없었다.

## 로그를 끄고 프로파일러를 붙여 봤다

<Q>관측 도구나 로그가 지연을 만든 것은 아닐까?</Q>

처음에는 프로파일링으로 지연 구간을 직접 찾으려 했다. 하지만 해당 Nsight 측정에서는 약 18~96%의 오버헤드와 불완전한 trace가 나타났다. 프로파일러가 모든 환경에서 이 정도 비용을 낸다는 뜻이 아니다. 이번 설정의 trace를 원래 실행과 같은 것으로 취급할 수 없었다는 뜻이다.

로그는 별도 대조 실험으로 확인했다. 파일 출력, 출력 폐기, 로그 비활성화를 균형 순서로 비교했다. 로그 off에서는 대표 시간이 Q8 약 3.08%, F16 약 2.04% 줄었다. 그러나 로그를 꺼도 지연은 남았다.

로그가 비용의 일부라는 가설은 지지됐지만, 로그가 모든 간헐적 지연의 원인이라는 가설은 지지되지 않았다. 관측 도구를 붙였을 때는 원인을 추적하기 전에 **그 도구가 실행을 얼마나 바꾸는지**부터 확인해야 했다.

## 지연을 두 가지로 나누다

<Q>GPU를 사용하는데 CPU 시간은 왜 봤나?</Q>

GPU 연산을 요청하고 동기화하는 호스트 코드도 실행 경로의 일부다. 호스트 계측에서 전체 경과 시간과 주 스레드의 CPU 실행 시간을 함께 보면, 같은 “느려졌다”를 조금 더 구체적으로 나눌 수 있었다.

<Figure caption="이번에 관찰한 두 지연 양상. 각각 하나의 확정된 원인에 대응하는 분류는 아니다."><DecodeLatencyPaths /></Figure>

CPU 실행 시간이 함께 늘어나는 경우에는 호스트 작업의 비용이나 실행 속도가 달라졌을 가능성을 살펴봐야 한다. 경과 시간만 늘고 CPU 실행 시간이 거의 늘지 않는 경우에는 CPU에서 실행되지 않은 구간을 확인해야 한다. 경과 시간에서 CPU 시간을 뺀 값은 비실행 시간의 근사이며, 그것만으로 runnable 대기와 다른 대기를 정확히 구분할 수는 없다.

CPU 고정 조건에서는 해당 배치의 꼬리가 관찰되지 않았다. 다만 적은 사건 수의 “관측되지 않음”을 “제거됨”으로 해석하지 않았다.

## CPU를 강제로 옮기면 느려지는가

<Q>자연 지연을 기다리지 말고, 의심한 조건을 직접 만들면 어떨까?</Q>

주 스레드를 CPU 6과 8 사이에서 이동시키는 조건과 그대로 두는 조건을 비교했다. 이동 작업 자체는 측정 타이머 밖에 두었다. 그 실험에서 이동 조건의 decode는 짝 비교 기준 Q8 **7.669%**, F16 **2.315%** 느렸다. 두 형식 모두 24개 짝 전부에서 이동 조건이 느렸다.

그다음에는 도착한 CPU에서 활동한 뒤 측정하면 회복되는지를 봤다. GPU decode 예열을 넣으면 페널티가 크게 줄었다. 하지만 이것만으로 GPU 캐시나 모델 데이터 예열이 원인이라고 결론 낼 수는 없었다. CPU도 함께 활동했기 때문이다.

그래서 비슷한 시간 동안 세 가지를 비교했다.

| 측정 전 활동 | 확인하려던 것 |
| --- | --- |
| sleep | 시간이 지나기만 해도 회복되는가 |
| CPU-only 정수 연산 | GPU·모델 데이터 접근 없이 회복되는가 |
| GPU decode 예열 | 실제 decode 활동으로 회복되는가 |

이동 조건에서 Q8은 sleep 뒤 약 18.181ms, CPU-only 뒤 14.881ms, decode 예열 뒤 14.823ms였다. F16은 각각 21.876ms, 19.447ms, 19.440ms였다. CPU-only 활동으로도 대부분 회복됐다.

이는 GPU나 모델 캐시만으로 회복 현상을 설명하기 어렵다는 근거다. 그렇다고 CPU 주파수가 유일한 원인으로 확정된 것은 아니다. 또 복구 작업에는 타이머 밖의 비용이 든다. **예열 뒤 측정 구간이 빨라진 것과 전체 요청 시간이 개선된 것은 다르다.**

각 후속 실험에는 KV 복원 등 프로토콜 차이가 있다. 서로 다른 캠페인의 시간이나 변화율을 같은 baseline 위의 연속 개선으로 합치지 않았다.

## 주파수 가설은 어디까지 확인했나

<Q>그렇다면 CPU 주파수가 모든 지연의 원인이었나?</Q>

CPU 이동 뒤 정수 작업을 1ms 구간으로 나눠 실행하고 APERF/MPERF 카운터를 읽었다. 이동 후 주파수와 처리량이 떨어졌다가 함께 회복되는 양상을 확인했다. CPU 실행 상태가 관여한다는 근거는 강해졌다.

그러나 정수 작업의 궤적이 실제 decode의 궤적과 같다는 보장은 없다. 따라서 자연 decode에서 주파수를 함께 관측하는 실험을 별도로 했다. 기본 affinity와 주 스레드 고정, 주파수 계측 off/on을 교차해 24라운드·192프로세스를 실행했다. 강제 이동이나 추가 복구 활동은 넣지 않았다.

자연 지연은 세 건이었다.

| 사례 | 관측한 사실 | 남은 한계 |
| --- | --- | --- |
| CPU 실행 시간 증가형 두 건 | 전체 약 22.39ms·22.54ms, CPU 이동 동반 | 주파수 계측 off에서 발생해 주파수 하락 여부를 모름 |
| CPU 비실행 시간 증가형 한 건 | 전체 21.6405ms, CPU 시간 19.0399ms, 차이 약 2.6016ms | 누가 CPU를 점유했는지와 정확한 대기 상태는 모름 |

마지막 사례에서는 비자발적 문맥 전환 5회가 관측됐고, 유효 주파수는 같은 프로세스의 다른 반복과 비슷했다. 이 한 건을 큰 주파수 하락으로 설명할 근거는 없었다. 하지만 주파수가 없는 나머지 두 건까지 포함해 “자연 지연의 주파수 가설이 반증됐다”고 말할 수도 없었다.

카운터 해석에도 한계가 있다. APERF/MPERF는 해당 CPU의 활동을 측정하므로 다른 작업이나 인터럽트가 포함될 수 있다. 서로 다른 CPU의 값을 빼지 않도록 이동을 관측한 구간은 무효 표시했지만, 관측 사이에 이동했다 돌아오는 경우까지 모두 잡지는 못한다.

또 Q8과 F16의 정상 주파수 수준도 달랐다. 정수 작업에서 본 약 4.6GHz를 F16 decode의 정상 기준으로 대입할 수 없었다. **작업 종류가 다른 실험의 기준값은 그대로 옮겨 쓸 수 없다.**

## 왜 여기서 진단을 멈췄나

<Q>원인을 완전히 밝혀내지 못했는데 본 실험으로 돌아가도 되나?</Q>

이 시점에서는 스케줄러 이벤트를 더 추적하거나 CPU 정책을 바꾸는 실험도 가능했다. 하지만 원래 목적은 시스템의 모든 지연 원인을 규명하는 것이 아니라, 구조 차이를 비교할 측정 기반을 마련하는 것이었다.

누적 결과를 Claude Code의 Fable과 두 차례 검토하면서 해석을 점검했다. 첫 답변의 “자연 지연에서 주파수 기전이 반증됐다”, “2% 미만은 식별할 수 없다”는 주장은 증거가 부족하다고 반론했고, 재검토에서 철회됐다. 모델 간 합의를 증거로 삼은 것이 아니라, 원자료로 뒷받침할 수 없는 주장을 걷어내는 과정이었다. 이 탐색은 사람이 주도했으며 H1/H3의 에이전트 성과로 계산하지 않았다.

종료 질문은 **“기존에 관심 효과로 둔 10% 수준의 차이를 탐색할 근거가 있는가?”**로 정했다. 추가 GPU 실험 없이 기존 240프로세스를 재분석했다.

- 원자료의 25회와 앞 20회 제외·뒤 5회 평균을 대조했다.
- 이전 캠페인과 바이너리·모델·runner 해시, 환경 및 런타임 일치를 확인했다.
- 프로세스 평균들의 CV는 최대 **3.873%**였다.
- 각 조건의 모집단 중앙값에 대한 순서통계 신뢰구간을 계산했을 때, 관측 중앙값 대비 한쪽 최대 편차는 **4.502%**였다.

표본 10개에서 두 번째~아홉 번째 정렬값을 쓰는 구간의 신뢰수준은 독립·동일분포의 연속 표본이라는 가정 아래 약 97.85%다. 이는 **각 조건의 구간**이지 24개 전체의 동시 구간도, 두 구조 차이의 직접 검정도 아니다. 더 보수적인 동시 구간에서는 폭이 10%를 넘는 조건도 있었다. 따라서 모든 조건에서 10% 차이를 확증했다고 표현하지 않았다.

보조적으로 관측된 분포에서 두 그룹을 복원추출하고 ±10%의 차이를 넣었을 때도 높은 구분 가능성이 나왔다. 하지만 이 분석은 관찰하지 못한 꼬리나 날짜별 드리프트를 만들어 내지 못한다. 미래 검정력의 보장으로 사용하지 않았다.

이 근거는 구조 파일럿을 계속할 실용적인 이유로는 충분하다고 판단했다. 새 구조에서 작은 차이를 주장할 때 필요한 검증까지 끝난 것은 아니다.

## 남긴 것은 원인 하나보다 측정 규약이다

<Q>다음 실험에서는 무엇을 고정하고, 무엇이 생기면 다시 조사할까?</Q>

전체 24개 항목의 반복 자료가 있는 기존 프로토콜을 우선 v1으로 고정했다. 로그 off나 pinning이 유망해 보여도 모든 구조에서 검증한 것은 아니므로, 새 조건을 기존 자료와 섞지 않는다. 이 규약의 수치에는 기존 로그 출력 비용이 포함된다.

| 항목 | 고정한 내용 |
| --- | --- |
| 실행 조건 | 고정 llama.cpp 커밋과 모델 해시, 전체 offload, threads 4, batch 512, ubatch 128, flash attention off, KV F16 |
| CPU·로그·계측 | 기본 affinity, stderr 파일 출력, host/MSR/Nsight 계측 없음, GPU 경계 상태 기록 |
| 반복과 대표값 | 조건·phase당 10프로세스, 각 20회 예열+5회 보존, 프로세스 평균들의 중앙값 |
| 순서와 기준 모델 | 순서를 무작위화한 라운드, 중간 Q8·S512 모델을 phase별 기준으로 반복 |
| 변동과 꼬리 | 원자료 보존, 대표값과 별도 보고, 느린 표본을 선택적으로 제거하지 않음 |
| 비용 | 로드·예열·실패를 포함한 전체 하드웨어 시간을 기록 |

기준 모델의 첫 5라운드와 뒤 5라운드 대표값이 5% 넘게 달라지면 배치를 검토 표시하기로 했다. 이는 앞으로 사용할 운영 규칙이며, 검증된 안정성 경계나 자동 삭제 기준은 아니다. 이 규약 전체를 자동 집행하는 실행기를 구현한 단계까지 마친 것도 아니다.

진단을 다시 여는 조건도 제한했다. 기준 모델의 드리프트나 실행 조건 불일치가 발생하거나, 새 구조의 불확실성이 목표 효과 비교를 막거나, 배포 환경의 꼬리 지연 자체가 연구 목표가 될 때다. 자연 이동형 지연의 주파수 연결과 CPU 비실행 구간의 정확한 원인은 미해결 사항으로 남겼다.

## 다음에 같은 실험을 한다면

이번 과정에서 가장 크게 바뀐 것은 “같은 모델을 같은 옵션으로 실행했다”라는 말의 의미다. 실제 측정값에는 모델 구조뿐 아니라 실행 전 상태, 호스트 동작, 계측 방식까지 들어 있었다.

그래서 다음에는 먼저 비교하려는 효과 크기와 대표값을 정하고, 예열·로그·CPU 배치·반복 수를 규약으로 고정할 것이다. 대표 성능과 꼬리 지연을 별도로 보며, 인위적으로 재현한 현상을 자연 지연의 원인으로 곧바로 일반화하지 않을 것이다. 그리고 진단을 시작할 때 종료 기준도 함께 정할 것이다.

에이전트 연구에도 같은 원칙이 필요하다. 규칙을 제시하는 능력뿐 아니라 그 규칙의 적용 범위를 제한하고, 반증 실험을 선택하며, 증거가 부족할 때 판단을 보류하는 능력을 평가해야 한다. 이를 위해 정답을 아는 합성 기기와 보류된 개입 조건, 동일한 측정 접근 권한과 비용 장부를 준비해야 한다.

다음 단계는 고정된 규약으로 Q8 아키텍처 후보를 비교하는 것이다. 이후 실제 타깃에서 다시 확인하고, 최소 에이전트와 PySR 등의 기준선을 같은 예산으로 비교할 계획이다. **이번에 끝낸 것은 그 연구를 시작하기 위한 측정 진단이다.**
