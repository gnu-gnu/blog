**왜 NaN이 났나** — 세 가지가 겹쳤습니다.

- **복소수로 남은 대각**: `LMMSEInterpolator1D`의 `h_var = diag_part(cov_mat)`은 실수부를 취하지 않습니다. 공분산 대각에 아주 작은 허수 jε이 있으면 파일럿 없는 행의 분모가 0이 아니라 jε이 됩니다.
- **0일 때만 듣는 가드**: `divide_no_nan`은 분모가 정확히 0일 때만 막으므로, jε은 통과하고 스케일 |s| = 2R/|ε|이 폭주합니다.
- **float32 오버플로**: `s*(s-1)`이 Inf가 되고 여기에 0을 곱해 NaN이 됩니다. 조건은 대략 0 &lt; |ε| ≲ 1.08e-19·R입니다.

이 NaN은 추정기 최종 출력에 보이지 않고, 검출기에 가서야 TB당 LLR 40개로 나타납니다.

**TL;DR** — 같은 Sionna 식에 공분산만 바꿔 넣었을 때의 결과입니다.

| 공분산 | 대각 허수부 | 결과 |
| --- | ---: | --- |
| complex64로 누적 | 5.0e-15 ~ 6.3e-11 | 비유한값 없음 |
| complex128로 누적 후 complex64로 저장 | 1.25e-25 ~ 1.71e-21 | **TB당 LLR 40개 NaN** |
| 위 공분산을 (R+Rᴴ)/2로 대칭화 | 0 | 비유한값 없음 |
| 대칭화 후 대각에 1e-10j 추가 | 1e-10 | 비유한값 없음 |
| 단위 공분산 대각에 1e-22j 추가 | 1e-22 | 비유한값 발생 |

정밀도를 올려 잔여물을 줄인 쪽에서만 터졌습니다. 공분산 저장 경계에서 대칭화해 막았고, LMMSE 재구현의 추정 구간은 3,808 µs/TB에서 346 µs/TB로 11.0배 줄었습니다. 측정 환경은 Sionna 0.18·TF 2.17·RTX PRO 6000 Blackwell이며, 스케일 식의 재현은 공식 Sionna 1.2.2 CPU 컨테이너에서도 확인했습니다.

## 들어가며

5G NR 상향 링크 시뮬레이션으로 수신기 여러 개를 여러 채널 조건에서 평가하고 있었습니다. 조건을 바꿔 가며 반복해야 하는 실험인데 기존 구조로는 한 번에 약 8.5시간이 걸릴 것으로 나와서, 먼저 평가 시간을 줄이기로 했습니다.

가장 느린 경로인 `LMMSEInterpolator`를 다시 구현하면서 원본과 복호 판정이 같은지 비교했는데, 세 번째 검증에서 256 TB가 전부 어긋났습니다. 저장한 LLR을 보니 원본 쪽에 NaN이 있었습니다.

이 글에서는 평가 시간을 줄이려던 작업이 어떻게 이 NaN으로 이어졌는지, 왜 정밀도를 올린 쪽에서만 터졌는지, 그리고 CPU로 돌렸다면 어땠을지를 측정한 내용을 다룹니다.

## 평가 시간의 81%가 LMMSE 경로였습니다

**GPU로 옮기고 배치를 키워도 LMMSE만 남았고, 이 경로에서 GPU 커널이 도는 시간은 13%뿐이었습니다.**

처음에는 CPU에서 도는 부분이 많으니 GPU로 한 번에 처리하면 해결될 것이라고 생각했습니다. 배치를 키우고 eager 실행을 그래프 실행으로 바꾼 뒤 경로별로 다시 쟀습니다.

| 경로 | 조치 전 (µs/TB) | 조치 후 (µs/TB) |
| --- | ---: | ---: |
| 신경망 추론 | 16,320 (eager) | 166.3 (그래프, 배치 1024) |
| LDPC 복호 | 6,501 (배치 8) | 214.7 (배치 1024) |
| LMMSE 추정·검출 | 8,683 (배치 8) | 3,803.5 (배치 256) |

LMMSE는 평가 연산 시간 합의 약 81%였고, 배치 256에서 피크 GPU 메모리가 이미 11.09 GB라 더 키우기도 어려웠습니다. Nsight Systems로 추적해 보니 3,803.5 µs 중 GPU 커널 활동은 약 497 µs였습니다.

나머지 시간을 쓰는 곳은 두 군데였습니다. 내삽 필터를 구하는 `tf.linalg.lstsq(fast=False)`는 CPU로 내려갔다가 돌아오는 경로였고, 슬롯마다 변하지 않는 288×288 공분산을 배치 전체로 브로드캐스트하면서 배치당 약 2.9 GB의 복사가 일어났습니다.

## 고유분해로 11배 줄이고, 판정 일치를 관문으로 걸었습니다

**수치 경로가 바뀌는 구현을 택한 대신, 원본과 비트·CRC 판정이 한 건이라도 다르면 멈추도록 했습니다.**

`lstsq`를 그대로 두고 중복 계산만 없애면 원본과 수치 동작이 가장 비슷하지만 CPU 왕복이 남습니다. 공분산을 미리 고유분해해 캐시하면 슬롯마다 GPU에서 대각 나눗셈과 행렬곱만 하면 되는 대신 수치 경로가 달라집니다. 속도를 우선해 후자를 택했습니다.

| 단계 | 조건 | TB-조건 비교 | 원본과 판정 불일치 |
| --- | --- | ---: | ---: |
| 1 | 표본 공분산 | 7,680 | 0 |
| 2 | 정합 공분산 | 3,072 | 0 |
| 3 | UMi 공분산 | 256 | **256** |

첫 두 단계에서 추정 구간은 3,808 µs/TB에서 346 µs/TB로, 피크 메모리는 11.09 GB에서 330 MB로 줄었습니다.

## 세 번째 관문에서 256 TB가 전부 어긋났습니다

**정답 기준을 따로 만들어 비교하니 고유분해 구현은 판정이 맞았고, NaN은 원본 경로에만 있었습니다.**

UMi 공분산 조건에서 payload가 다른 TB가 156건, CRC가 다른 TB가 100건으로 합집합이 256건이었습니다. 수치 경로를 바꾼 쪽은 새 구현이니 어느 쪽 문제인지부터 가려야 했는데, 저장한 LLR을 보니 원본 쪽에 NaN이 있었습니다.

NaN이 있다고 새 구현이 맞다고 볼 수는 없어서, 같은 추정기 정의를 numpy complex128로 옮긴 정답 기준을 따로 만들었습니다. 먼저 정합 공분산에서 원본과 맞는지 확인한 뒤 세 경로를 맞춰 봤습니다. 고유분해 구현은 정답 기준과 판정이 모두 같았고(LLR 최대 차이 0.001633), 원본은 TB마다 정확히 40개의 LLR이 NaN이었습니다. 명목 잡음을 넣어도 같은 자리에서 나왔습니다.

## NaN은 최종 출력에 보이지 않았습니다

**오차 분산에서 생긴 NaN이 인덱스 기본값을 타고 한 부반송파로 모인 뒤 사라졌다가, 검출기에서 다시 나타났습니다.**

`LMMSEInterpolator`의 최종 출력에는 NaN이 하나도 없어서, 출력에 `isfinite`를 걸어 두었어도 지나갔을 것입니다. 단계별로 값을 기록해 따라가 보면 경로는 다음과 같습니다.

```text
주파수 단계  파일럿 없는 심볼 10개 × 288 RE → err_var 2,880개 NaN
곱셈 마스크  NaN × 0 = NaN, 그대로 남음
시간 단계    _add_err_var_indices 기본값 [0,0,0,0,0]
             → 2,880개가 0번 부반송파 행렬 대각 한 곳으로 합쳐짐
lstsq        이 부반송파에 0을 반환 → h_hat이 13심볼 모두 0
추정기 출력  err_var는 유한한 ext_mat로 재계산 → 전부 유한
검출기       0번 부반송파 데이터 RE 10개 × 4비트 → LLR 40개 NaN
```

## 분모의 아주 작은 허수가 가드를 통과했습니다

**파일럿 없는 행에서는 분모가 정확히 0이 되도록 되어 있는데, 대각의 허수 잔여물이 이를 깨뜨립니다.**

Sionna 1.2.2 기준 1141~1151행이며 0.18에도 같은 식이 있습니다.

```python
err_var_c = tf.complex(err_var, self._rzero)
h_var = tf.linalg.diag_part(cov_mat)
s = tf.math.divide_no_nan(2.*h_var, h_hat_var + h_var - err_var_c)
...
err_var = s*(s-1.)*h_hat_var + (1.-s)*h_var + s*err_var_c
```

파일럿 없는 행에서는 `h_hat_var`가 0이고 `err_var`는 대각의 실수부입니다. 대각이 실수면 분모가 정확히 0이어서 `s`도 0이 됩니다. 그런데 `err_var`는 앞에서 `tf.math.real`을 거치는 반면 `h_var`는 복소수 그대로라, jε이 남아 있으면 분모가 jε이 됩니다. 이번 사례에서 `s`의 최대 절대값은 2.57e25였습니다.

허수부를 일부러 고려하지 않았을 가능성도 생각해 봤지만 코드만으로 의도를 단정할 수는 없었습니다. 공분산은 수학적으로 Hermitian이어야 하니 입력이 실수 대각을 지킨다고 전제했을 수 있습니다. 그래서 라이브러리 결함이라기보다, 입력 계약에서 아주 조금 벗어난 값과 스케일 계산이 만나 생긴 강건성 문제로 판단했습니다.

공분산이 특이에 가까워서 생겼을 가능성도 확인했습니다. 파일럿 없는 행의 필터는 조건수와 상관없이 0이고, 단위 공분산에 1e-22j만 더해도 재현되므로 이 가설은 접었습니다.

## 정밀도를 올리자 잔여물이 위험 대역으로 들어갔습니다

**잔여물이 크면 안전하고, 아주 작으면 터지고, 정확히 0이면 다시 안전합니다.**

이 공분산은 원래 complex64로 누적했는데, 양의 정부호 단언에 걸려서(최소 고유값 약 -1.6e-5) 누적만 complex128로 올린 것이었습니다. 정밀도를 올렸으니 더 안전해야 할 것 같은데 올린 쪽에서만 NaN이 났습니다.

이해하려고 같은 식을 JS로 옮겨 봤습니다. `0.1 + 0.2 - 0.3`이 0이 아닌 것은 JS에서도 익숙한 현상이고, `Math.fround`로 float32를 모사하면 Inf × 0도 그대로 재현됩니다.

```js
0.1 + 0.2 - 0.3                                   // 5.551115123125783e-17
const big = Math.fround(Math.fround(1e20) * Math.fround(1e20)) // Infinity
big * 0                                           // NaN
```

복소 연산을 float32로 옮겨 ε만 바꾼 결과입니다(R = 1.604).

| 대각 허수부 ε | \|s\| | `err_var` |
| ---: | ---: | --- |
| 1e-5 | 3.2e5 | 유한 |
| 1e-18 | 3.2e18 | 유한 |
| 1e-19 | 3.2e19 | NaN |
| 1e-25 | 3.2e25 | NaN |
| 0 | 0 | 유한 |

경계는 약 1.08e-19·R입니다. 표의 "유한"이 맞는 값이라는 뜻은 아닙니다. ε이 0이 아니면서 경계보다 크면 `err_var` 실수부는 R이 아니라 -R이 되어 0으로 잘립니다. 다만 파일럿 없는 행의 `err_var`는 시간 단계 전에 마스크로 지워지므로, 코드상 판정에는 영향이 없는 것으로 봅니다. double로 계산하면 같은 입력이 유한하고 ε이 1e-160까지 내려가야 같은 현상이 나왔으니, float32에서 이 경계가 실제 잔여물 크기와 겹치는 것이 문제였습니다.

그렇다고 complex64가 안전하다고 볼 수는 없습니다. 측정한 공분산의 |s| 최대값 약 6.5e14와 float32 경계 약 1.8e19 사이는 약 4.5자릿수로, 이 입력에서 터지지 않았다는 뜻이지 그만큼의 여유가 보장된다는 뜻은 아닙니다. 양의 정부호 단언도 나중에 보니 필요 이상으로 엄격했고, 수치 허용 오차를 둔 PSD 검사로 충분했습니다.

## 잔여물은 곱셈 순서에 따라 달랐습니다

**같은 연산을 TF CPU로 돌리면 잔여물이 정확히 0이었습니다. FMA와 누산 순서를 바꾼 모델로 커널별 패턴을 상당 부분 재현할 수 있었습니다.**

수식상 `h·hᴴ`의 대각은 실수이므로 잔여물은 곱셈 구현에서 생깁니다. CPU로 돌렸다면 어땠을지 x86 TF 2.17에서 합성 복소 정규 입력(288×13, 배치 30)으로 쟀습니다. GPU는 3,334회, CPU는 200회 평균입니다.

| 입력 | GPU 대각 허수부 | GPU NaN 원소 | CPU 대각 허수부 |
| --- | ---: | ---: | ---: |
| complex64 | 8.4e-14 ~ 3.7e-11 | 0/288 | 0 |
| complex64를 complex128로 캐스트 | 7.1e-23 ~ 3.6e-20 | 288/288 | 0 |
| complex128 | 6.1e-23 ~ 1.3e-19 | 285/288 | 측정 안 함 |

합성 입력이라 값이 실제 공분산과 같지는 않지만 크기 범위는 비슷합니다. 그런데 왜 TF CPU는 0이고 GPU는 0이 아닐까요. 대각의 허수부는 항마다 `aᵢ·aᵣ - aᵣ·aᵢ`입니다. 두 곱을 각각 반올림하면 같은 값이 되어 정확히 지워지지만, 한쪽 곱을 FMA로 계산하면 반올림 없는 곱에서 반올림한 곱을 빼게 되어 곱의 반올림 오차가 남습니다. 한 누산기에 더하고 빼는 순서라면 누산 중 반올림도 남습니다.

C로 곱셈 순서만 바꿔 288×13 합성 입력 2,000개에 돌려 봤습니다. 위 그림의 패턴이 어디까지 맞는지 보기 위한 모델입니다.

| 계산 순서 | complex64 | 캐스트 | complex128 | 비슷한 실측 |
| --- | ---: | ---: | ---: | --- |
| 곱 둘 반올림 후 뺌, 또는 누산기 분리 후 뺌 | 0 | 0 | 0 | TF CPU, numpy einsum |
| 한쪽 곱만 FMA | 최대 5.8e-7 | 0 | 최대 1.0e-15 | numpy BLAS 5.2e-7, 0, 9.2e-16 |
| 한 누산기에 전부 더한 뒤 뺌 | 최대 3.3e-6 | 35.4%, 최대 4.4e-15 | 최대 7.4e-15 | cuBLAS GEMM 6.1e-7, 9.5%, 2.7e-15 |

numpy BLAS 경로는 모델과 패턴과 크기가 모두 비슷합니다. 캐스트 입력이 0인 것은 24비트 값 둘의 곱이 double에 정확히 담겨 곱의 반올림 오차가 없기 때문입니다. cuBLAS는 캐스트 입력에서 일부만 0이 아니라는 패턴은 같지만 비율과 크기가 맞지 않아서, 내부가 정확히 이 순서라고 볼 수는 없습니다. Hermitian 전용인 `Zherk`는 캐스트 입력에서 정확히 0이었습니다.

그래서 "GPU 문제인가"는 둘로 나눠서 봐야 했습니다. 잔여물을 폭주시키는 식은 플랫폼과 무관해서 공식 Sionna 1.2.2 CPU 컨테이너에서도 같은 입력으로 재현됐습니다. 반면 입력을 만드는 잔여물은 커널에 달려 있어서, 공분산을 TF CPU로 계산했다면 이번 일은 일어나지 않았을 가능성이 있습니다.

## 공분산 저장 경계에서 대칭화해 막았습니다

**(R+Rᴴ)/2만으로 비유한값이 사라졌고, 결과를 보기 전에 적어 둔 예측 네 가지도 모두 맞았습니다.**

대칭화하면 대각 허수부가 정확히 0이 되어 `divide_no_nan`이 의도대로 동작합니다. 실제 사례에서 대각 이외의 원소는 하나도 바뀌지 않았습니다. 대칭화한 공분산으로 기준 조건 4개를 256 TB씩 원본과 고유분해 구현에 넣어 불일치가 없는 것을 확인한 뒤 전체 평가를 끝까지 돌렸습니다.

원인을 제대로 이해했는지 보려고 예측을 먼저 적었습니다. complex64 누적, 대칭화 후 1e-10j 추가, 전체 complex128 계산은 비유한값이 없고, 단위 공분산에 1e-22j를 더하면 생긴다는 예측이었고 네 가지 모두 그대로 나왔습니다.

Sionna 코드는 고치지 않았습니다. `h_var`에 `tf.math.real`을 거는 것이 자연스러운 수정으로 보이지만 이 수정 자체는 검증하지 않았습니다.

## 최신 Sionna의 1e-12 가드는 NaN을 막지만 전력이 작으면 추정값을 0으로 만듭니다

**전력을 1e-13배로 줄이면 NaN 없이 추정값 전체가 0이 됐고, 시스템 레벨 채널에서는 공분산에 드롭별 전력을 넣었을 때만 나타났습니다.**

Sionna 2.1.0에서 `LMMSEInterpolator`는 제거됐습니다. 후속 `LMMSEChannelEstimator`의 내부 `_LMMSEEstimator1D`도 대각은 복소수 그대로이지만, 분모를 `denom.abs() > 1e-12`로 막습니다(2.1.0 기준 2056~2060행). 이 가드가 이번 문제를 막는지 공식 배포본을 CPU 컨테이너에 설치해 돌려 봤습니다. 격자는 14심볼·64 부반송파, 파일럿 심볼은 2개, 채널은 Sionna의 `tdl_*_cov_mat` 공분산에서 합성했고, 2.2.0도 결과가 같았습니다.

먼저 대각에 허수 잔여물을 넣어 봤습니다.

| 대각 허수부 ε | 비유한값 | `h_hat` 최대 차이 |
| ---: | --- | ---: |
| 1e-25, 1e-21, 1e-19, 1e-13 | 없음 | 0 |
| 1e-12 | 없음 | 1.7e-6 |
| 6e-11 | 없음 | 4.0e-6 |
| 1e-8 | 없음 | 1.0e-5 |

이번 NaN은 실제로 막혔습니다. ε이 1e-12 이상이면 가드를 통과하지만 출력 차이는 1e-5 이하입니다. 앞서 본 대로 파일럿 없는 행의 `err_var`가 마스크로 지워지기 때문으로 봅니다.

문제는 전력 쪽이었습니다. 시간·주파수 공분산을 α배, 수신 신호를 √α배, 잡음을 α배로 일관되게 줄이면 이론상 추정값은 √α배로 비례해야 합니다.

| 전력 배율 α | 비유한값 | 이론값 대비 상대 오차 | `h_hat`이 0인 비율 |
| ---: | --- | ---: | ---: |
| 1 ~ 1e-12 | 없음 | 3e-11 이하 | 0% |
| 1e-13 ~ 1e-16 | 없음 | 1.0 | **100%** |

1e-13부터는 경고도 비유한값도 없이 추정값 전체가 0이 됩니다. 분모 전체가 1e-12 아래로 내려가 정상 파일럿 행까지 가드에 걸리기 때문입니다.

이 경계가 실제로 닿는 값인지 Sionna 2.2.0의 UMa·UMi 채널을 경로 손실과 함께 정규화 없이 생성해 확인했습니다. 시나리오별 1,000드롭, 단일 안테나, 3.5 GHz이며 잡음은 열잡음과 송신 전력 23 dBm으로 잡았습니다. 경로 이득이 -130 dB 이하인 드롭은 UMa 54.2%, UMi 17.9%로 드물지 않았습니다. 다만 가드가 걸리는지는 공분산에 전력을 어떻게 넣느냐로 갈렸습니다.

| 공분산의 전력 표현 | -125 dB 이하 드롭의 `h_hat`=0 | -125 ~ -120 dB | -120 dB 초과 |
| --- | ---: | ---: | ---: |
| 드롭별 전력 반영 | **100%** | **43~46%** | 0% |
| 시나리오 평균 전력 하나 | 0% | 0% | 0% |
| 전력 1 그대로 | 0% | 0% | 0% |

즉 경로 이득이 낮은 것만으로는 걸리지 않고, 정규화하지 않은 단말별 표본으로 공분산을 추정해 작은 전력이 공분산까지 들어갔을 때만 걸립니다. 입력이나 공분산을 정규화해 쓰는 일반적인 경우에는 닿을 일이 드물 것으로 봅니다. 다만 전력을 뺀 공분산을 절대값 입력에 그대로 쓰면 가드는 지나가지만, -140~-130 dB에서 NMSE가 정규화 기준 약 -10 dB에서 -1~0 dB로 나빠졌습니다. 이것은 공분산 전력 불일치의 영향이며 가드와는 별개입니다.

이전 버전의 가드는 정확히 0일 때만 듣고, 지금 가드는 절대값에 묶여 있습니다. 분모를 R에 대한 상대값으로 비교하면 두 경우를 함께 막을 수 있어 보이지만, 이 수정은 Sionna에서 돌려 보지는 않았고 식으로만 계산했습니다. 비슷한 이슈는 아직 찾지 못했습니다.

## 마치며

- **판정 일치 관문이 원본의 결함까지 드러냈습니다.** 속도만 쟀다면 만나지 못했을 NaN이고, 두 구현만 비교했다면 어느 쪽 문제인지 가르지 못했을 것입니다.
- **벽시계 시간만으로는 병목을 알 수 없었습니다.** GPU 환경에서도 이 경로의 GPU 커널 활동은 13%였습니다.
- **`isfinite`는 최종 출력만 봐서는 부족했습니다.** 오차 분산 같은 중간값을 봐야 했습니다.
- **0 가드는 정확히 0일 때만 듣고, 절대값 임계값은 값의 크기에 묶입니다.** 2.x의 1e-12는 NaN을 막았지만 전력이 1e-13배인 입력의 추정값을 전부 0으로 만들었습니다. 복소수에서 실수여야 할 값은 타입 변환 경계에서 강제하는 편이 안전합니다.
- **정밀도를 높이는 것이 항상 안전 쪽은 아니었습니다.** 0.18부터 1.2.x까지의 `LMMSEInterpolator`에 직접 만든 공분산을 넘긴다면 대칭화를 검토할 만합니다.

남은 문제도 있습니다. cuBLAS 내부의 계산 순서는 확인하지 못했습니다. 1e-12 가드 문제는 단일 섹터 1,000드롭의 UMa·UMi 채널에서 확인했고, 실제 프로젝트에서 드롭별 전력을 공분산에 넣는 경우가 얼마나 되는지는 모릅니다. 상대 기준 수정도 Sionna에서 검증하지 않았습니다. 실제 채널 공분산의 잔여물은 GPU에서 저장한 값만 쟀고 다른 커널로는 재지 않았습니다. `tf.math.real` 수정도 검증하지 않았고, 이 NaN이 복호 성공률에 얼마나 영향을 주는지도 따로 재지 않았습니다.
